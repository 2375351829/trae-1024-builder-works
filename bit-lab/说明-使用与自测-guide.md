# 说明-使用与自测-guide —— 1024 位运算 · Bit Lab

> **作品 A《1024 位运算 · Bit Lab》**：2048 的骨架，但每个格子是一段**能被解码的比特串**。
> 4×4 = 16 个 64 位槽位 = **1024 位寄存器**；格子里的大数字 = 这 64 位里 **1 的个数**；
> 合并 = 真实的**按位或 `A OR B` + 补位**（运算过程可回看）；16 格全部满格 → **1024 个点全亮**。
>
> 交付物：`index.html`（单文件、零依赖、零外部请求）+ 本文档。

## 三、玩法与规则（与规格 A2 的对应）

### 3.1 基础规则

1. **4×4 = 16 个槽位，每槽 64 位**（`Uint8Array(64)`，元素 0/1）。16 槽 × 64 位 = **1024 位寄存器**。
2. **瓦片数值 = 该 64 位串中 1 的个数**（popcount），取值档位 `2 / 4 / 8 / 16 / 32 / 64`。
3. **同值合并**：两个数值相同的格子相撞 → 结果 `C = A OR B`（逐位或），再把 C **补足到 2 倍的 1**；
   若并集不足，则在空闲位补位，演出中标注「**补 N 位**」。
4. **新格**：每次有效移动后随机生成 1 个新格，**90% 为 2 个 1、10% 为 4 个 1**（实测 90.1%）。
5. **满格（64 个 1）不再参与合并**：64 × 2 = 128 超出 64 位寄存器容量。
6. **计分**：合并得分 = 新瓦片数值；每补 1 位额外 +5 分；达成胜利 +1024 分。
7. **最高分**写入 `localStorage`（键 `bitlab.v1`），刷新后仍在。
8. **进度条**「已点亮 X / 1024 位」= 16 槽当前 1 的个数之和。

### 3.2 规则修订（⚠️ 与规格原文的差异，已获 Lead 认可；**同样写在界面上**，不藏在代码注释里）

| # | 规格原文 | 本实现 | 原因 |
|---|---------|--------|------|
| 1 | 「16 格全部达到 64 → 胜利」 | **新增「终局补位」**：满格堆到 **12 个**后，新生成的格子直接补满 64 个 1；走投无路时也可点击未满格手动「终局补位」 | **按位或合并是「1 的总数守恒」的运算**（2 个 v 合并后仍是 2v 个 1，总数不变），且 4×4 棋盘从零构建一个满格至少需要 **5 个空位周转**（满格最多堆到 12 个）。若不补位，1024 位在数学上**永远凑不齐**，胜利态不可达 |
| 2 | 「IPv6 八段」示例 `2001:0db8:0000:0000:0000:ff00:0042:8329` | 64 位放进**低 64 位（后 4 组）**，前 4 组左补 `0000` | 对齐规格示例的「接口标识符」写法：整址 128 位，本槽只占低 64 位 |
| 3 | 未提及 | **满格（64 个 1）不参与合并** | 64 + 64 = 128 > 64 位，物理上不可能；不排除会让 2048 式的连吞 bug 复发 |

> **补充说明（避免评审误判）**：开局 **16 格全部预置**（每格随机 2 或 4 个 1）是**刻意的设计**——
> 不是常规 2048 的「2 格开局」。目的是让玩家**第一眼就看到完整的 8×8 位点阵**，并且 16 格 × 64 位
> 天然构成一个 1024 位寄存器。由于每格是随机预置，开局「已点亮」通常在 **32—64 位**之间
> （多次实测 32 / 34 / 38 / 40），这是**正常随机开局**，不是伪造数据。
> 界面棋盘下方也写明了「开局 16 格全部预置，方便你第一眼看到完整的 64 位点阵」。

### 3.3 「64 位解读」四个视角的**位序约定**

- 位序：索引 **0 = 最高位（2⁶³）**，索引 **63 = 最低位（2⁰）**；格子里 8×8 点阵按行优先从左到右、从上到下排列。
- **uint64 十进制**：把 64 位按上述位序约定当成一个无符号整数。
- **IPv6**：64 位 → 后 4 组（16 进制 4 位/组），前 4 组补 `0000`。
- **8 字节 HEX + ASCII**：每 8 位 = 1 字节，**高位在前（big-endian）**；不可打印字符显示为 `.`。
- **纳秒时间戳**：把 64 位当成 **Unix 纳秒数**，输出统一按 **UTC+8**。

**已验证的输入输出对照（可直接复核）**：

| 输入位串 | uint64 | IPv6 | 8 字节 HEX | ASCII | 纳秒时间戳（UTC+8） |
|---------|--------|------|------------|-------|--------------------|
| 全 0 | `0` | `0000:0000:0000:0000:0000:0000:0000:0000` | `00 00 00 00 00 00 00 00` | `........` | `1970-01-01 08:00:00.000` |
| 全 1（64 个 1） | `18446744073709551615` | `0000:0000:0000:0000:FFFF:FFFF:FFFF:FFFF` | `FF FF FF FF FF FF FF FF` | `........` | `2262-04-11 23:47:16.854` |
| 仅 bit63 = 1 | `1` | `0000:0000:0000:0000:0000:0000:0000:0001` | `00 00 00 00 00 00 00 01` | `........` | `1970-01-01 08:00:00.000` |
| 浏览器实测样本（槽位 #13，数值 2） | `24` | `0000:0000:0000:0000:0000:0000:0000:0018` | `00 00 00 00 00 00 00 18` | `........` | `1970-01-01 08:00:00.000`（原值 24 ns）|
| 浏览器实测样本（槽位 #9，数值 8） | `90159955627214880` | `0000:0000:0000:0000:0140:5000:8020:0820` | `01 40 50 00 80 20 08 20` | `.@P.. . ` | `1972-11-09 20:25:55.627` |

> 面板还额外给出：**槽位编号（第几行第几列 / 第几槽）**、**本槽贡献多少个 1**、**累计点亮到第几槽为止的位数**、**该槽最低置 1 的位号**。

## 四、右侧「1024 的 6 种身份」知识卡 —— 最终文案与数值出处

> 这张卡是作品的主题升华位（也呼应作品 B 的 IPv6 解读面板）。**所有数值均可核对**，出处如下。

| 身份 | 界面文案 | 数值出处 / 核对 |
|------|---------|---------------|
| **位** | 2¹⁰；二进制 `10000000000`，共 **11 位** | 2¹⁰ = 1024 ✓。二进制表示为 1 后面跟 10 个 0，即 **11 个二进制位**（第 10 位为 1，故需 11 位才能表示；常见误写「10 位二进制」不成立）|
| **字节** | 1024 B = **1 KiB**（IEC, 2¹⁰）= **1.024 kB**（SI, 10³）| IEC：1 KiB = 1024 B ✓；SI：1 kB = 1000 B，故 1024 B = **1.024 kB**（SI 下不能写成「1 KB」）|
| **网络** | IPv6 的 **/64** 前缀块 = 2⁶⁴ = **18,446,744,073,709,551,616** 个地址 —— 运营商分配给**单个用户**的最小区块 | /64 即 64 位前缀 = 2⁶⁴ 个地址 = 18446744073709551616 ✓。/64 是 RIPE NCC / ARIN 对**终端用户**（subscriber）分配的最小前缀粒度，恰好等于本作品单槽的 64 位 ✓ |
| **时间** | 1024 秒 ≈ **17 分钟**；1024 分钟 ≈ **17 小时** | 1024 ÷ 60 = 17.07 分 ✓；1024 ÷ 60 = 17.07 小时 ✓ |
| **像素** | 32 × 32 = **1024 px** —— 正是本作品胜利位图的尺寸 | 32×32 = 1024 ✓，与胜利画面位图网格完全一致 |
| **寄存器** | 16 槽 × 64 位 = **1024 位** = **128 字节** | 16×64 = 1024 位 ✓；1024 ÷ 8 = **128 字节**（= 0.125 KiB；注意不是 8 KiB，8 KiB = 65536 位）|

> **注**：以上三处（位 / 字节 / 寄存器）在初稿讨论中出现过常见笔误（10 位二进制 / 1 KB(SI) / 8 KiB），
> 定版已按上表校正，可直接被逐条核对。

### 5.3 完整流程到胜利态

**方式 A（评审/录制用，1 步到达）**：点「演示：查看胜利画面」→ 16 格瞬间满格 → 弹出胜利画面
（1024 点位图 + 荧光绿笔刷横扫 + 像素吉祥物 + 绿色 bokeh）→ 成就卡解锁 → 填昵称 → 下载 PNG。
浏览器实测：`won = true`、`lit = 1024`、`bitmapOn = 1024`、成就卡 PNG 生成成功。

**方式 B（正常玩法）**：合并 → 满格逐步堆积 → 满格达到 12 个后进入「终局补位」，新格直接补满 →
16 格全满 → 胜利。由于按位或合并不增加 1 的总数（只有新格 +2/+4），正常玩法需要 **数百步** 才能凑齐
1024 位（每次有效移动约 +2.2 位），这是机制本身决定的节奏，非缺陷。

1. **正常玩法需要数百步才能到 1024 位**：机制上「按位或守恒 1 的总数」，只有新格带来净增（+2/+4）。
   为此提供「演示：查看胜利画面」按钮，供评审与录制直接查看终局与成就卡。
2. **移动端浏览器禁止自动下载时**，成就卡按钮会因浏览器策略静默失败（Chrome/Safari 在多数桌面与移动端允许
   `data:` URL 下载）。可在桌面端下载；本页无 `alert()`，失败时以横幅提示。
3. **`localStorage` 不可用（无痕模式 / 站点策略）时**，最高分只保存在内存中，不报错、不影响游玩。
4. 页面内 `window.__bitlab` 是**只读状态快照**（供自动化自测使用），不参与玩法、不影响任何逻辑。
