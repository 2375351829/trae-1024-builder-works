## 三、数据源：自主探查（重点说明）

> 这一节同时也是作品本身的技术论点：**浏览器不让网页直连论坛，那网页怎么才能自己拿到数据？**

### 3.1 实测结论：**浏览器直连必被拦（但这不等于只能靠人手动）**

| 检查项 | 实测结果 |
|---|---|
| `GET /t/topic/325833.json` 状态码 | `200` ✅ 接口本身完全公开可读 |
| 响应头 `Access-Control-Allow-Origin` | **不存在**（带 `Origin: https://example.com` 请求头复查，依然为空） |
| 响应头 `Vary` | `Accept-Encoding`（**不含 `Origin`** → 说明该站未开启 CORS） |
| 真实浏览器里 `fetch()` 的结果 | `TypeError: Failed to fetch`（Chrome 控制台：`blocked by CORS policy: No 'Access-Control-Allow-Origin' header is present`） |

**第一版**据此把取数设计成一条「主路径」：打开 JSON 链接 → 复制全文 → 粘贴 → 解析。
**但那有个致命问题**：一个叫「实况墙」的作品，数据却要人手搬 —— **它不实况**。

### 3.2 第二版：把限制从「设计」升级成「工程问题」

**核心思路**：既然**网页**这一跳被同源策略挡住，那就换一个**不受同源策略约束的执行环境**去取数，再把结果变成网页可直取的东西。

| 环节 | 做法 | 关键点 |
|---|---|---|
| 取数 | `06-工具-tools/抓取楼层-fetch-floors.mjs`，分页拉 `/t/325833.json?page=N` 到底 | Node 运行，**不受浏览器同源策略约束** |
| 调度 | GitHub Actions 工作流 `fetch-floors.yml`，**每 15 分钟** + 手动触发 | `permissions: contents: write`；推送前 `git pull --rebase` 避免与人工推送撞车 |
| 落地 | 写成静态文件 `data/floors.json`（GitHub Pages） | Pages 对静态资源返回 **`access-control-allow-origin: *`** → 网页可**跨源直取** |
| 消费 | 页面按优先级**依次探查 6 条通道，命中即止** | 见下表 |

**页面探查通道（按优先级）**

| # | 通道 | 说明 |
|---|---|---|
| 1 | 本站镜像（同源） | `../data/floors.json`；页面从 Pages 打开时同源，**零 CORS 成本** |
| 2 | 本站镜像（跨源） | `https://2375351829.github.io/…/data/floors.json`；靠 `ACAO: *` 跨源直取，**file:// 双击打开也能用** |
| 3 | 论坛直连 | `https://forum.trae.cn/t/topic/325833.json`；官方哪天开启 CORS 即刻生效 |
| 4—5 | 公共 CORS 代理 ×2 | `api.allorigins.win` / `api.codetabs.com`；与上面完全独立的第三方路径 |
| 6 | RSS 通道 | `/t/topic/325833.rss`（只要最新 25 层，载荷小），用于镜像滞后时补鲜 |

**实测**：从 Pages 打开 → 命中通道 1，**0.30s**；本地 `file://` 双击打开 → 命中通道 2，**0.12s**。**全程不需要任何人复制粘贴 JSON。**

### 3.3 镜像只搬数据，不下判断（职责分离）

`data/floors.json` 的每行是 `[楼号, 时间戳ms, 用户名, 纯文本前 400 字]`，**不含有效性标志**。
「有效 / 严格」两套口径**一律由页面现场用同一套正则算**（`applyMirror()` / `applyRSS()` → `VALID_RE` / `VALID_MARK_STRICT`）。

> 这样镜像与页面永远不会各算各的，让 213 / 201 / 12 这些数字打架 —— **数据通道与判定逻辑，职责必须分开。**
> 实测：镜像载入后 `valid=213 / validStrict=201 / validVariant=12`，与内置基线**完全一致**。

### 3.4 页面为什么默认不弹红色报错

跨域受限是**已知的平台特性**，不是故障；而且现在它已经被架构解决了。因此页面默认展示的是一条**中性信息条**，
探查成功后转为**成功条**，并附**可展开的「探查日志」**（逐条列出：通道 / 耗时 / 结果或失败原因）——
**把「找路」的过程摊开给读者看**，包括失败的那些。

> **已自主探查完成**：命中通道 **本站镜像（跨源）**，取回 **361** 条楼层，耗时 **0.47s**。当前最高 364 楼 · 参与者 233 · 最后回复 2026-10-21 00:44。　·　镜像采样于 2026-10-21 03:54
> 页面会每 3 分钟自动再探查一次，**全程不需要人工复制粘贴任何 JSON**。

只有当**全部通道都没命中**时，页面才切到告警条（含逐条失败原因与「手动导入 JSON」兜底入口）。

### 3.5 降级策略（硬要求项，逐条落地）

| 要求 | 实现 |
|---|---|
| 顶部醒目提示 + 重试按钮 | 全部通道未命中 → `showBanner('err', …)` +「⟳ 重试探查」按钮（黑底荧光绿投影） |
| 保留最近一次成功快照 | `localStorage['floorwall.snapshot.v1']`，写入时机 = 每次成功探查后；页面启动时若存在且比内置快照新，则自动恢复 |
| **绝不能白屏** | 探查失败只走降级分支，DOM 主体照常渲染；`boot()` 外层还有 `try/catch` 兜底，初始化异常也会降级为最小可用页面 |
| 自动重探 | `setInterval(180_000)`（3 分钟；镜像每 15 分钟更新，故 60s 太频繁）；页面不可见（`document.hidden`）时暂停；**全部通道未命中后熔断暂停**，避免重复触发浏览器网络告警（手动重试即恢复） |
| 手动导入（兜底） | 降级为「所有自动通道都没命中」时的最后手段，面板标题已改为「手动导入 JSON（备用通道）」 |

## 四、有效回复的判定（两套口径都算、都展示）

### 4.1 为什么要先解码 HTML

Discourse 会把话题标签渲染成：

```html
<p><span class="hashtag-raw">#我是</span> 1024Builder#</p>
```

「我是」与「1024Builder」之间隔着一个 **HTML 标签**，而不是空白字符。
所以直接在原始 `cooked` 里用字符串匹配会**漏判 12 层**。正确做法是**先把 `cooked` 解码成纯文本再匹配**。

### 4.2 判定规则

| 口径 | 规则 | 命中层数 |
|---|---|---|
| **宽松（主判定）** | 解码纯文本后匹配 `/我\s*是\s*1024\s*Builder/i` | **213 层** / 360 层回复 |
| 严格字面（对照） | 解码纯文本后含连续字面 `我是1024Builder` | **201 层**（把主帖公告一并计入则为 202） |
| 两者之差 | 含空白变体写法 | **12 层** |

**含空白变体的 12 个楼号**：66 / 94 / 113 / 114 / **129** / 134 / 160 / 244 / 294 / 313 / 336 / 358

**为什么主判定取宽松**：官方原文是「每个社区账号仅计 1 次有效参与；**重复回复、灌水或与活动无关的内容**不计入有效楼层」——
排除的是**内容**，**不是排版格式**。`#我是 1024Builder#`（中间带空格）且四行填写齐全，它不是灌水、也不是与活动无关，
它就是一次完整的有效参与。

### 4.3 同一个「顺延一楼」，两种口径落在不同楼层（本作品最有技术含量的地方）

官方规则原文：「盖到 128 楼，256 楼，512 楼，1024 楼等四个指定特殊楼层的朋友…**如所在楼层是无效回复，则顺延一楼**」

| 里程碑 | 宽松口径（主判定） | 严格字面口径（对照） |
|---|---|---|
| **128** | `128✗ → 129✓` → **129 楼「硬气一点」** | `128✗ → 129✗ → 130✗ → 131✗ → 132✗ → 133✓` → 133 楼「琦哈哈」 |
| **256** | `256✓` → 256 楼「鱼香肉丝没鱼老婆饼里没老婆夫妻肺片没老婆夫妻」 | `256✓`（一致） |
| 512 | 未达成 | 未达成 |
| 1024 | 未达成 | 未达成 |

页面上的**里程碑轨**会把两条链一起展示：主判定那条高亮，另一条以「口径对照」小字列出 —— **把规则的歧义算给读者看**。

### 已知的三个坑（记录在案，便于复现时省时间）

| # | 坑 | 表现 | 处理 |
|---|---|---|---|
| 1 | **Discourse 的话题标签包裹** | `<span class="hashtag-raw">#我是</span> 1024Builder#` —— 「我是」与「1024Builder」之间是 HTML 标签而非空白 | 先 `stripHTML` 解码成纯文本，再宽松匹配；否则漏判 12 层、128 楼顺延终点算错 |
| 2 | **论坛限流 503** | 短时间内并发请求分页 JSON 会返回 503 | 采样加载改为串行 + 700 ms 间隔，失败退避到 1.5 s |
| 3 | **Windows PowerShell 的编码陷阱** | `Get-Content -Raw` + `Set-Content -Encoding UTF8` 往返会把含中文的 UTF-8 文件按 GBK 解码再写回，**不可逆地损坏**（约 274 行被破坏） | 一律用 `read`/`edit`/`write` 工具改文件；必须用脚本改时用 Node `fs` 并显式 `'utf8'` |
